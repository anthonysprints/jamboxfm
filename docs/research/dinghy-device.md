# Dinghy audit for the first JamBoxFM hardware experiment

Read-only audit, 2026-10-13. Repository: https://github.com/zvenson/dinghy.
Pinned source: `d44df7db09b98ccad2f1233b8f83f5f09c04829e` (2026-10-12).
Clone: `/workspace/scratch/fm1-device-plan/dinghy`; source checkout remains clean.
No upstream scripts, builds, compiler downloads, firmware downloads, installers or hardware actions were run.

## Recommendation

Keep the present Sloop/JamBox musical core. Dinghy is a useful minimal example of separating the musical application from the updater/recovery platform, not a shortcut around the target compiler or a reason to replace our working sequencer/UI/DSP. A first device candidate can keep **musical sessions in RAM** while retaining **the bounded flash driver, updater and rescue path**. Those are separate responsibilities. Disabling both flash support and OTA, as our prototype currently does, prevents the convenient updater route back to Sloop; it is not required merely because songs must not be saved yet.

“RAM-only session” is different from “run an experimental application entirely from RAM without installing it.” Dinghy builds an ordinary flash/XIP application. Only its flash routines and update loader execute from RAM. It supplies no complete flash-free application launch workflow. [App map](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/app.ld#L3-L30), [loader map](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/loader/loader.ld#L3-L19).

## What is confirmed in source

- **Target:** JieLi AC791N / vendor pi32v2 compiler, 1 MiB flash with the specific JEDEC value `0x856014` accepted for writes. Package builder names `AC791N`, assumes chip key `0x980F`, and puts the app in the existing family layout. The loader checks the device's actual key before erasing. These facts do not establish compatibility with every possible FM-1 hardware revision. [Package target](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/tools/fm1pkg_make.py#L24-L30), [key/chip gate](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/loader/ldr_core.c#L105-L125), [JEDEC check](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/loader/loader.c#L58-L75).
- **Application/platform division:** `dinghy.c` includes `platform.c` and supplies `app_audio` and `app_main`; this is one compilation unit, not a packaged HAL library. The minimal app is a four-voice sine instrument. Platform keeps interrupts, watchdog, USB, updates, settings and boot/recovery. [Contract](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/docs/API.md#L3-L45), [platform](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/platform.c#L1-L18).
- **Controls/audio:** physical 27 keys, 14 buttons, seven encoders and master; scan at 10 kHz. Audio uses 256 stereo frames at 44.1 kHz (~5.8 ms); the app fills zeroed Q15-scale `int32_t` buffers, then platform applies master, clips, feeds USB audio and shifts for the DAC. USB audio also supports 48 kHz through the inherited USB path; this is not a claim that the app DSP itself runs at 48 kHz. [Panel contract](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/docs/API.md#L58-L84), [audio ISR](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/platform.c#L191-L251).
- **Memory:** XIP app slot `0x8DFBC` bytes; `.data+.bss` 96 KiB; pool 336 KiB; separately placed RAM flash code and stacks. Linker enforces its regions. Hardware audio timing, particularly our full four-part engine, still requires measurements; Dinghy's much smaller app does not validate JamBox headroom. [Memory map](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/app.ld#L11-L30), [timing rules](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/docs/RULES.md#L28-L45).

## Updater, recovery and the route back to Sloop

1. **Normal app:** `platform_poll()` feeds watchdog, services updater identity/requests, and handles ROM-UBOOT requests. OTA can stage a validated loader before resetting into it. Dinghy deliberately compiles `FELUCCA_OTA=1`. [Defaults and write bounds](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/platform.c#L60-L92), [poll](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/platform.c#L254-L277).
2. **Application rescue:** OCT− alone at boot enters a minimal USB updater before normal audio/settings/app initialization. Two pending failed boots lead there automatically; a failure in rescue proceeds to ROM on the next warm boot. This depends on retained noinit state and working early application startup. [Bootguard](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/bootguard.h#L7-L29), [startup order](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/platform.c#L305-L340).
3. **Not a second firmware bank:** `recovery.c` explicitly requires intact application startup, RAM flash driver and USB stack. Rescue skips normal audio, settings, projects and UI; entering rescue alone does not write flash. This is valuable for isolating our experimental musical layer but is not an unconditional unbrick guarantee. [Recovery constraints and operation](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/recovery.c#L1-L4), [rescue startup](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/recovery.c#L41-L69).
4. **Install protocol:** USB-MIDI M-UPGRADE SysEx, host-served package reads, stage-one firmware validation/staging then stage-two RAM loader writing. Known custom loader requires marker `FELUCCA-LOADER-1`; official loader is accepted only with its known CRCs and a matching first 16 KiB flash head. `OTA_AREA=0xE0000`, staging length `0x5000`; update record at `0xE4F00`. [OTA protocol/layout](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/ota.c#L3-L29), [loader acceptance](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/ota.c#L269-L339).
5. **Custom loader rollback compatibility:** runs at `0x01C0A800`, checks chip key/known flash, writes app sectors `[0x4000,0x93000)`, never the flash head. It verifies sectors/package CRC and retains update records on failure so the loader can resume after reset/power loss. It also erases validated stale update records found in the record search region; this is not a blanket promise that every arbitrary foreign data format is untouched. [Loader contract](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/loader/ldr_core.c#L3-L34), [record cleanup](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/loader/ldr_core.c#L91-L102).
6. **Do not enable `FELUCCA_OTA_RAMONLY`:** its name concerns the updater's commit record, not musical session persistence. The source explicitly says it loses power-loss resume and can leave a broken loader after a power cycle. [Warning](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/ota.c#L373-L389).
7. **Host installer:** Python CLI uses `mido`/`python-rtmidi`, confirms before install, checks package CRC/loader marker, resumes only identities matching `ota-FM-1_9\d\d`, and verifies the restarted app's expected identity. Its `--info` queries running identity. No local web installer is included; README directs users to the external firmware hub or Python CLI. [CLI/protocol](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/tools/fm1_install.py#L4-L22), [resume and package validation](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/tools/fm1_install.py#L341-L385), [confirmation](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/tools/fm1_install.py#L466-L490).
8. **ROM fallback is distinct:** SysEx `F0 22 24 35 7D F7` sets `uboot_req` even when `FELUCCA_OTA=0`; the running main loop must honor it. This reboot requests `usb_update_mode` through the boot mailbox. Dinghy docs link FM-1-transporter for deeper recovery, but Dinghy itself does not implement that host transport. Its availability and actual owner-device restoration path must be verified separately; having this code is not a guarantee that a broken app can receive the soft key. [Ungated soft key](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/usb.c#L675-L723), [mailbox entry](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/hal/fm1_sys.h#L117-L130), [transporter reference](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/docs/RULES.md#L47-L56).

## Storage separation and useful deltas

Dinghy's flash write guard permits only updater staging and a dedicated 4 KiB settings sector at `0xFC000`. Its 256-byte settings block uses magic `DNGY`, length and CRC, then writes the header last. **This sector overlaps the family's existing globals area**, so copying Dinghy's settings code into JamBox would still destroy Sloop globals on save even though its magic differs. For the first JamBox candidate, use the updater-only flash range and leave all project/global/user-sample/FM6 persistent operations disabled, including boot-time format/import/cleanup of musical stores. Keeping `ota_boot_cleanup()` for its own staging is a separate updater duty. [Guard](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/platform.c#L69-L72), [settings writes](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/platform.c#L135-L170), [flash regions](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/hal/fm1_flash.h#L37-L54).

Byte comparison against our original Sloop `8fad1a15ff59d5c3ed0bfe2d7a9ae90962cf4d5e`:

- Identical: `app.ld`, `crt0.S`, `ota.c`, `bootguard.h`, loader files, package builder and almost all HAL files. Recovery change is the app-name string. IRQ difference is comments. Flash-header differences remove Sloop's extra FM6/sample write ranges.
- **Useful substantive USB delta:** Dinghy increases OTA reply queue timeout from 200 to 500 ms and tracks an interrupted SysEx; before the next reply it emits a standalone `F7` to end the interrupted frame. This deserves a focused transport test if ported; do not copy the entire stripped platform. [Delta implementation](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/src/usb.c#L815-L854).
- Dinghy's Python installer port filter is narrower than our Sloop version (it drops `sloop|clipper`). Our broader existing filter is useful for the explicit return-to-Sloop route. Preserve our installer rather than replace it unquestioningly.
- Package naming is `FM-1_99N` for Dinghy; its included RAM loader still uses `ota-FM-1_900`. Docs recommend selecting an unused `FM-1_9NN` app identity, but explicitly say there is no registry. Do not invent a supposedly reserved JamBox ID or reuse Dinghy's. [Identity guidance](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/docs/MAKE-IT-YOURS.md#L23-L33), [loader identity](https://github.com/zvenson/dinghy/blob/d44df7db09b98ccad2f1233b8f83f5f09c04829e/firmware/loader/loader.c#L3-L20).

## Concrete first-candidate gates

1. Obtain the genuine pinned pi32v2 compiler through an authorized reachable official source/environment; run an unchanged target baseline and retain ELF/map/disassembly, compiler/SDK hashes, app/loader/package hashes and static check output. Dinghy does not remove this blocker.
2. Split the existing JamBox prototype's low-level flash/update capability from musical persistence, preserving early bootguard/OCT− rescue/ROM entry and existing Sloop core. Restrict app writes to the OTA staging region; do not import Dinghy's overlapping settings writer or re-enable Sloop persistence wholesale.
3. Exercise host updater/loader validation and interrupted-update/resume cases already present in Sloop, and add a check that disabled musical persistence cannot write any Sloop data region. Dinghy's small host rendering harness does not replace those tests.
4. Before a device experiment, identify that owner's current firmware/hardware/flash assumptions, retain a known-good Sloop package and backup appropriate personal content, and establish which updater/rescue/ROM path can actually restore it. Demonstrate the route back on the actual device; do not infer it from browser/native tests.
5. First hardware candidate: RAM session, no autosave or store migration, minimal marked JamBox UI, keys/encoders/audio/MIDI checked incrementally, then measure full JamBox ISR timing and static memory headroom. Public release/flashing readiness follows successful device checks, not merely a `.fwsc` file.

These are recommendations from the audited code, not completed hardware validations or authorization to flash.
